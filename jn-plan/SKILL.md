读取 PRD 和项目现状，把工作拆成子任务正文及依赖清单。单独调用只产内容，发布和调度交给 JN 或用户明确指定的调用方。

## 拆分前

PRD 必须足以说明目标、边界、整体方案和验收；缺少会影响拆分的内容时交回 `jn-intent` 补齐。项目规则和术语表存在才读，验证命令从受影响模块实际配置中查，不强制类型检查。

核对代码现状与 PRD。已确认的取舍不重新选型；出现范围或重要风险变化时交回 PRD，修改需重新应用 `renhua` 并记录适用的确认。局部文件、函数和类型组织留给实施者，但计划不能省略实施锚点：必须写出当前入口、数据流或状态、目标行为、第一处阻塞点和验证落点。只写“完善后端”“增加校验”“联调前端”不算计划。

## 先形成可执行的路线

在拆任务前，先用项目事实写一段“现状 → 目标 → 路线”，至少包含：

- **现状**：用户或调用方从哪里进入，经过哪些已查证的模块、接口或状态；不确定的地方标为未知。
- **目标**：完成后用户能观察到什么行为；重要成功、失败、重试和刷新场景分别写清。
- **阻塞步骤**：哪些工作必须先完成才能让后续工作有真实输入；每步写交付物，不写抽象阶段名。
- **并行边界**：哪些工作流互不写同一份共享状态，可以并行；共享写入、迁移或顺序敏感的部分必须串行并说明原因。
- **验证落点**：每个交付物如何在真实运行面检查，检查输出应证明什么；不能只列“跑测试”或“确认无误”。

计划优先描述动作和证据，而不是章节、文件数量或技术名词。每个动作都应能回答“谁在什么位置做什么，产出什么，怎样知道做对了”。如果读者仍需要回到聊天记录猜范围，先补计划，不要继续拆任务。

## 拆任务和依赖

按可交付、可检查的行为拆，每项要能在独立上下文中完成；确有必要的准备任务写明交付物和验证方式。不按文件或技术层机械拆，不区分大小需求；一项工作也用同一任务模板。

拆分时显式写出以下四项，即使某项不适用也要说明原因：

1. **阻塞优先**：先做能解除不确定性或提供真实输入的步骤。
2. **独立工作流**：把互不重叠的模块、服务或用户路径分开；共享文件或共享状态不得假装并行。
3. **共享状态**：指出谁维护事实、谁只读投影、并发写入和重试如何处理；能拆开就先拆开，不能拆开才安排串行。
4. **最小安全拆分**：说明为什么这是最小而且可验收的单元；单项任务也要说明为什么不再拆。

读取 [子任务模板](references/task.md)。每项写必要背景、范围、约束、验收、前置交付物和适用检查。只摘与本项相关的项目规则原文，标出处；整体设计仍以父 PRD 为准。

草稿用 T1、T2 标识，依赖只表示实际需要的前置交付，不把排列顺序当依赖。检查自依赖、循环、重复工作和遗漏；并行任务注明各自范围，避免把同一份代码同时交给多人。不同会话间的代码是否可访问由执行阶段再次检查。

每条 PRD 验收标准至少有任务覆盖；“未来的可能性”和范围外未决问题不自动加入本次任务。需要多个任务共同验证的条件明确留给整体 Review，不能只分散到局部检查。

完成拆分后做一次“反云里雾里检查”：逐项删掉“处理、完善、支持、优化、联调、相关代码、必要改动”等没有对象和证据的词，替换成具体行为、入口、交付物和预期观察。任务正文中的“做”至少要能对应一个真实用户场景或调用方场景；“检查方式”至少要给出实际命令或可重复的操作步骤，以及通过时应看到的结果。

## 交付

交回完整任务正文，以及“草稿标识 / 标题 / 前置任务 / 交付物 / 对应验收”的导览表；不额外创建 tracker 之外的进度文件。发布后由调用方用真实 Issue 链接或本地相对路径替换临时标识并建立关系。

完整 PRD 和任务拆分一起供用户确认，一次确认覆盖后续实施。JN 已持有相应授权时直接记录，不逐项请求确认。修改既有任务时读取当前正文和执行记录，保留已完成事实，不用全新草稿覆盖用户记录。
